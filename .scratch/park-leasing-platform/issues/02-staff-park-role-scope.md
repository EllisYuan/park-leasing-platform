## What to build

可操作的最小园区建档与员工授权管理：维护园区、部门、员工账号与角色，在指定园区给员工分配角色，形成园区—员工—角色三方授权；员工可兼岗，同一员工可在不同园区承担不同角色，不把全局角色与园区集合笛卡尔组合扩大权限。数据访问同时受操作权限与本人/部门/授权园区范围约束，系统管理员不自动获得经营数据。

修改密码、停用账号或调整授权后，已有会话失效或重新鉴权后生效。列表、详情、统计、附件与后续导出共用同一服务端范围解析，不信任前端提交的归属；前端菜单与按钮的隐藏不能替代后端拒绝。提交人不能审核自己单据的规则以服务端统一校验交付，07、08 的审批命令必须复用。

- 园区是授权边界，部门是园区内的组织单元，员工账号是全局身份；角色与园区的组合逐条授权。
- 角色分配按“员工 + 园区 + 角色”记录，同一员工跨园区持有多条授权，不聚合为全局角色。
- 范围解析集中在服务端统一组件，列表、详情、统计与附件入口调用同一解析。
- 权限变更后已有会话的处理方式与 01 的会话失效机制对齐，不新增长期令牌。
- 前端只依据后端返回的权限渲染入口，不自行推断数据范围。
- 测试覆盖相同员工在两个园区的访问差异与系统管理员无园区角色的拒绝。

## Acceptance criteria

- [ ] Migration 建立园区、部门、员工账号、角色与园区角色授权表，空库迁移后可启动，使用真实 MySQL 验证。
- [ ] 系统管理员创建员工账号后该账号可登录；停用后不能登录，且已有会话在下一次请求即失效并要求重新登录。
- [ ] 修改密码或调整园区角色后，该员工已有会话失效或重新鉴权，权限变化生效。
- [ ] 同一员工在两个园区分别持有不同角色时，两个园区的业务查询各自只返回其被授权范围，不串权也不合并放大。
- [ ] 系统管理员未获园区角色时，不能读取或操作该园区经营数据，拒绝响应不泄露范围外内容。
- [ ] 员工可同时持有多个角色；部门范围校验使普通员工只能看到本人或本部门数据。
- [ ] 提交人自审限制以服务端统一校验交付，同一账号对同一单据的提交与审核组合被拒绝，该规则供后续审批单据复用。
- [ ] 未授权的列表、详情、统计与附件接口均返回拒绝，不能依靠隐藏入口保护数据。
- [ ] UI 可完成园区创建、员工与部门维护、按园区分配角色，结果持久化到 MySQL；不同权限账号看到相应菜单与数据。
- [ ] 以真实 MySQL 与认证上下文执行 HTTP/API 测试并保留原始输出，未执行的验证不写为通过。
