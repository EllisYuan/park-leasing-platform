# 22: 手动公海、分配、领取与转交

Status: open
Label: ready-for-agent
Type: task
Blocked by: 06
Spec: [平台Spec](../spec.md)
User stories: 30, 31, 32

## What to build

招商经理按数据范围将线索分配给专员或转交他人，保留历史负责人与原因可查；专员可手动把线索退回公海；公海领取是原子操作，多人同时领取只有一人成功。联系人查看与导出需额外鉴权。不做按未跟进天数自动回收，阶段跳过不补造历史，真实跟进与阶段事件保留。公海不是所有人可访问的公开客户资料。

分配、转交、领取与退回都作用于 06 的同一线索实体，本票只增加负责人历史与公海状态，不复制线索数据，也不改写既有跟进与阶段事实。

## Acceptance criteria

- [ ] 招商经理将线索分配或转交给专员，负责人历史（原负责人、新负责人、操作人、时间、原因）持久化到 MySQL 并可查询。
- [ ] 专员将持有线索手动退回公海，退回原因与时间可查；退回后线索进入公海列表。
- [ ] 并发领取：多个专员同时领取同一公海线索，只有一个成功，其余返回冲突或已领取；在真实 MySQL 上以唯一约束或条件更新验证，不依赖先查后改的应用层判断。
- [ ] 权限边界：非经理不可跨人分配；专员只能操作授权园区的线索；联系人查看与导出需额外权限，未授权请求被拒绝；不存在跨园区越权。
- [ ] 不实现按未跟进天数自动回收；不自动补造阶段、跟进或转化历史。
- [ ] 公海列表、分配、转交、退回与领取 UI 在后台可用，数据落库。
- [ ] 必要 migration（负责人历史、公海状态、联系人敏感字段鉴权所需结构）可空库执行并保留既有数据。
- [ ] 证据：真实 HTTP 与 MySQL 输出，含并发领取唯一与越权用例；未执行项如实标注。
