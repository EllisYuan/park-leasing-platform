# 05: 字典、公告与站内待办

User stories: 98

## What to build

业务字典维护、按范围发布公告、查看未读提示与站内待办及处理状态，提供可操作的页面与 API。公告按全局或园区范围发布，用户只看到其被授权范围内的内容；未读与已读状态持久化。待办列表展示待处理事项并支持处理状态流转。

消息刷新采用定时拉取，不使用短信、邮件或 WebSocket。本票至少接通一个真实来源形成闭环（如运营向指定范围内人员发布公告产生未读、或运营发起一条真实站内待办），后续业务事件逐票接入同一待办/未读服务并按业务键去重；不建立只有空表而没有真实来源的通用消息容器，也不引入可视化流程设计器。

- 字典按编码与名称维护，启用与停用状态可查询，业务模块按编码读取。
- 公告包含标题、内容、发布范围与发布时间，发布后按范围对用户可见。
- 待办包含事项、关联业务键、接收人、期限与处理状态，处理动作留痕。
- 未读按用户与公告/待办记录，标记已读只影响本人。
- 刷新使用定时拉取，不引入短信、邮件或 WebSocket 连接。
- 待办创建与去重通过业务键在服务端完成，重复调用返回已有记录。
- 范围过滤与个人待办归属在服务端判定。

## Acceptance criteria

- [ ] Migration 建立字典、公告、待办与未读状态表，空库迁移后可启动并使用真实 MySQL 验证。
- [ ] 字典项可新增、修改与停用，按编码查询；重复编码被拒绝，停用项不再作为新业务选项。
- [ ] 公告按全局或园区范围发布，范围内用户可见，范围外用户读取被拒绝且不泄露内容。
- [ ] 待办通过真实业务入口创建并出现在列表，处理状态变更后持久化；同一业务键重复写入不产生重复待办。
- [ ] 未读数与已读状态持久化，用户标记已读后刷新仍保持，不因前端刷新丢失。
- [ ] 定时刷新可更新列表与未读数，不依赖短信、邮件或 WebSocket；无轮询以外的推送机制。
- [ ] 用户只能读取自己的待办与其范围内的公告，读取他人待办或范围外公告返回拒绝。
- [ ] UI 可完成公告发布与查看、待办处理与未读提示，操作结果持久化到 MySQL。
- [ ] 使用真实 MySQL 与真实认证上下文执行 HTTP/API 测试并保留原始输出，未执行的验证不写为通过。
